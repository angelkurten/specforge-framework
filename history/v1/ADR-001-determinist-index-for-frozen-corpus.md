# ADR-001: Deterministic regex-built index over the frozen PRD/ADR corpus

**Status**: Proposed
**Date**: 2026-05-13
**Decision makers**: Framework maintainer, Tooling
**Context PRDs**: None
**Supersedes**: None

---

## 1. Context

specforge's corpus is monotonically growing and append-only: PRDs and ADRs are frozen snapshots, and `SYSTEM_ARTIFACT.md` files are the only living documents. The lead agent re-discovers the relational structure of this corpus on every authoring session by running `grep` over `Depends on`, `Supersedes`, `Impacted Projects`, gate-block `commit_hash` / `tests:` / `system_artifact_diff:` fields, and `Roadmap item:` headers (per `.claude/rules/hard-rules.md` #4 and `.claude/rules/workflow.md` step 2). At small corpus sizes this is cheap; as the corpus grows the same discovery has to happen for every new authoring session, every step-8 "resume a different Draft" branch, and every step-9 post-implementation re-review.

External research on graph-augmented retrieval (Microsoft GraphRAG, LightRAG, KET-RAG, "When to use Graphs in RAG" — ICLR'26) reports material token savings on multi-hop queries over document corpora, but at non-trivial indexation cost when entities/relations have to be extracted by an LLM. specforge's situation is unusual: the relations the lead agent cares about — PRD→sibling, PRD→PRD via Depends/Supersedes, PRD→commit, PRD→test file, PRD→`SYSTEM_ARTIFACT` section — are **already tagged** in YAML/Markdown headers by the format that `.claude/rules/prd-authoring.md` and `.claude/rules/gate-block.md` impose. They do not need to be extracted; they need to be parsed.

This ADR resolves whether to introduce a derived index of those relations.

## 2. Decision

We will build a **deterministic, regex-based index** of the corpus generated by a parser script (no LLM in the loop), serialized as JSON, regenerated on every merge to `main` via a git hook, and referenced from `CLAUDE.md` so the lead agent can load it at session start. The index represents PRDs, ADRs, siblings, commits, test files and `SYSTEM_ARTIFACT` sections as nodes; `Depends on`, `Supersedes`, `Impacted Projects`, `ships_at` (gate-block `commit_hash`), `covers` (gate-block `tests:`) and `documents` (gate-block `system_artifact_diff:`) as edges. The index is a derived artifact — frozen documents remain the source of truth.

## 3. Alternatives Considered

### Option A — Status quo (grep on demand)

The lead agent and reviewers continue to discover relations by grep at session time. No new artifact, no parser, no hook.

**Pros**:
- Zero maintenance surface.
- No derived artifact to drift out of sync with frozen documents.
- Already prescribed by hard-rule #4 and works for current corpus size.

**Cons**:
- Grounding cost grows with corpus size — the same chains are walked from scratch every session.
- Multi-hop queries (Supersedes chains, "what PRDs share a commit") require multiple grep+read rounds.
- Estimated 15-40K tokens per session of avoidable rediscovery at 30-100 PRDs (see §4).

### Option B — Full GraphRAG (Microsoft or LightRAG)

Use an LLM to extract entities and relations from PRD bodies; build community summaries; serve a query interface.

**Pros**:
- State-of-the-art on free-text multi-hop queries.
- Captures relations that live in prose, not just headers.

**Cons**:
- Indexation cost (LLM passes) on a corpus where the cited relations are already structured — paying to rediscover typed data.
- Microsoft's own published indexation costs ($20-500 per corpus; community reports up to ~$33K for large corpora) overshoot the value at specforge's size.
- Sensitivity to extractor model and silent extraction errors — a wrong edge is harder to debug than a missed grep.
- The corpus today is well under the ~1000-entity threshold where graph approaches reliably beat vector RAG (arXiv 2502.11371).

### Option C — Vector RAG over PRD bodies

Embed each PRD section, retrieve by semantic similarity.

**Pros**:
- Cheap to build, well-understood.
- Good for fuzzy thematic search ("PRDs about auth").

**Cons**:
- Specforge's high-value queries are **relational**, not semantic — vector retrieval does not answer "what PRDs ship in commit X" or "trace the Supersedes chain from PRD-042" well.
- Adds infrastructure (embedding model, vector store) for a marginal gain over grep + long-context Opus.

### Option D — Deterministic regex-built index *(chosen)*

A parser script reads headers and gate blocks, emits a JSON graph. No LLM, no embeddings.

**Pros**:
- 0 tokens of LLM for construction; cost is parser CPU time.
- Cannot hallucinate edges — every edge has a `file:line` provenance in a frozen document.
- Regenerable from source at any time; if the index is lost it rebuilds in seconds.
- Matches the framework's existing philosophy: PRDs are frozen, the index is a view, not a second source of truth.

**Cons**:
- Captures only what the formats encode. Relations stated in prose ("see §3 of PRD-017") are invisible.
- Adds one git hook and one parser to maintain (~200 LOC).
- Useful only as long as authors honor the canonical formats — but those are already enforced by hard-rules.

## 4. Consequences

**Positive**:

- Grounding step (`workflow.md` step 2) can consult the index before launching Explore agents — Explore agents then scope their reads instead of grep-walking the corpus.
- Hard-rule #11 (sibling registry discipline) and hard-rule #4 (no back-references, grep for newer PRDs) become O(1) lookups instead of corpus scans.
- Estimated token savings per authoring session (with caveat that these are predicted, not measured):

  | Corpus | Per-session saving | ROI |
  |---|---|---|
  | <30 PRDs | ~5-10K (10-15%) | unclear — overhead ≈ saving |
  | 30-100 PRDs | ~15-40K (20-35%) | positive from session one |
  | 100-300 PRDs | ~40-90K (30-45%) | clearly positive |
  | >300 PRDs | the flat index saturates; reconsider GraphRAG | |

- The index is a natural input for future tooling (visualisation of the Supersedes graph, dead-link detection in `Impacted Projects`, drift detection between §9 `tests:` paths and gate-block `tests:` list).

**Negative**:

- A new derived artifact in the repo. Must be regenerated; stale indexes mislead silently.
- The parser becomes a hidden dependency of `workflow.md` step 2. If it breaks, sessions degrade to status-quo grep — acceptable, but the failure mode must be visible (the loader should log "index missing, falling back to grep").
- Risk of authors trusting the index over the frozen documents. Mitigation: the index file carries a header comment naming the source-of-truth rule and its build timestamp.

## 5. Trade-offs Accepted

- We accept that relations stated only in prose (not in headers/gate blocks) stay invisible to the index. This is consistent with the framework's preference for structured, grep-able formats over free text.
- We accept a small maintenance surface (parser + hook) in exchange for eliminating LLM tokens from the construction path — the chosen design has zero ongoing API cost.
- We accept that at <30 PRDs the saving is marginal. The decision is justified by the slope, not the current value; specforge's whole premise is that the corpus grows monotonically.
- We accept that this ADR's token-savings numbers are **estimates** until validated empirically (see §6).

## 6. Signals to Reconsider

| Signal | Action |
|--------|--------|
| Empirical validation shows <10% session saving at 50+ PRDs | Supersede this ADR; remove parser and hook. |
| Authors start needing multi-hop free-text queries ("which architectural decisions changed after incidents in sibling X") | Open a follow-up ADR proposing LightRAG/LazyGraphRAG on top of the deterministic index. |
| Index drifts undetected from source documents more than once | Add a CI check that rebuilds the index and diffs it against the committed version. |
| Corpus exceeds 300 PRDs | Reopen — the flat JSON shape may need a proper graph database or community-summary layer. |
| Non-structured documents (meeting transcripts, ticket dumps) enter scope | Reopen — LLM extraction may earn its keep there. |

## 7. Cost to Reverse

Low. Remove the parser script, the git hook, and the reference from `CLAUDE.md`. The frozen documents are untouched; sessions revert to grep-based grounding. Estimated effort: under a day for one maintainer.

# Review a change

1. If you can already name a way the diff breaks its contract, it is a fix round, not a review: write the failing test and run the loop again first (change 2026-10-25-ledger-hardlink). Then run `python3 specforge/scripts/review_prep.py <change> --base <ref the branch started from>`. When the contract names a code sibling, add `--repo ../<sibling> --repo-base <ref the sibling's branch started from>` so the packet covers the sibling's diff too (change 2026-10-26-sibling-repos). For a change across several siblings, repeat the pair once per sibling, in order (change 2026-10-27-multi-sibling-review). Keep its full output: that is the packet.
2. **Exercise.** For a change with user-visible behaviour (a page, a CLI command, an HTTP route another repository calls), run that user-visible path end to end against the running system yourself, in a browser or with a real client, not a fake. Record the command or interaction, and what it showed, under `Exercised` in the evidence. Write `none — <why>` when the change has no such path. A release has one: its CLI. Pack it with the real npm (`npm pack --pack-destination <scratch>`; here `npm` may be a pnpm alias that cannot pack bundled dependencies), and run the tarball's `init` in an empty directory and its `update` over the previous version (change 2026-10-29-release-0-30-0 wrote `none` and was blocked). A Not checked entry on that path blocks review (change 2026-10-29-exercise-the-path: every test passed while the page was dead in a browser).
3. Dispatch the `specforge-reviewer` agent with the packet, the change folder and the mode from the contract's `Mode` line. Do not add your own opinion of the change to the brief. Do add the shell procedure: a new clone directory from `mktemp -d` under the scratchpad, every command run as `cd <clone> && …`, and a stop if the clone or the `cd` fails. The rule in the reviewer's own definition did not stop two reviewers from running in the real tree; the procedure in the brief did (changes 2026-10-29-audit-fixes-web and 2026-10-29-release-0-30-0).
4. Report the reviewer's `VERDICT` line and every blocker to the human verbatim. A BLOCK goes back to the loop or to the human, never past it. A reviewer's diagnosis enters the evidence only after the lead re-runs the command that shows it: a change once rewrote a correct line on a reviewer's cause that the same reviewer's next round refuted (change 2026-10-29-review-prep-lock-and-ci).
5. Before calling the change done, read the CI result for the pushed head commit. A red or missing run is a blocker, whatever the local runs said. The evidence's CI field names a run ID that exists for that exact SHA (`gh run list --commit <sha>`). Push the last code commit alone and wait for its runs before committing the evidence that names them: pushing several commits at once runs only the tip (change 2026-10-26-sibling-repos blocked on this), and a commit made after the last run (evidence, docs) needs its own run (change 2026-10-25-loop-budget, blocked twice on this).
